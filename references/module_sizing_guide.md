# 模块粒度指南

模块划分的核心矛盾：拆太细，跨模块连接和状态继承成本暴涨；拆太粗，单个实现任务超出上下文且容易带偏。本指南给出可量化的判定标准。

## 一、硬性上限

以下任一条件触发，**必须**继续拆分：

| 指标 | 上限 | 超出后果 |
|---|---|---|
| events.json 事件条目 | 300 条 | 单个实现任务上下文不足 |
| 原文行数 | 5000 行 | 无法在一个任务里完整读完 |
| 原文对白条数 | 800 条 | 台词容易遗漏 |
| 二级选择点（menu） | 8 个 | 分支组合爆炸，测试困难 |
| 模块入口前驱数 | 5 个 | 状态继承组合过多，应独立成汇合模块 |
| 出口数 | 6 个 | 连接关系难以核对 |
| 单文件 .rpy 行数 | 3000 行 | Ren'Py lint 变慢且难 review |

超过上限时不裁内容，只增加模块数，用显式入口/出口连接，并在模块 brief 中写清拆分顺序。

## 二、推荐区间

理想模块规模：

```
事件条目     80 ~ 200 条
原文行数     800 ~ 2500 行
对白条数     150 ~ 450 条
二级选择点   2 ~ 5 个
模块入口     1 ~ 3 个
出口         1 ~ 4 个
.rpy 行数    300 ~ 1500 行
```

这个区间下，单个实现任务通常能在一个上下文窗口内完成"读任务包 + 读原文 + 写代码 + 自查"。

## 三、拆分判定信号

出现以下信号说明该拆：

### 1. 一个任务读不完

实现时发现"必须同时打开三个文件才能写对这一段"——说明这段剧情和公共定义耦合过紧，或事件太密。拆成子场景，每个子场景带明确的入口状态。

### 2. 出口状态组合爆炸

模块有 4 个出口 × 3 个入口变体 = 12 种状态组合需要说明。超过 8 种时，把入口变体拆成独立的汇合模块，或把出口收敛。

### 3. 反复出现"这一步要看前面"

如果一个模块的 50% 时间花在往回读以理解上下文，说明它承担了两个原本独立的剧情单元。

### 4. 并行冲突

两个实现者都要改同一个公共文件或同一段剧情——边界没划对。

### 5. 测试路径太多

模块内需要验证的路径数 = 入口数 × 选择点组合数。超过约 20 条时，单个模块的验收成本过高。

## 四、不要拆的信号

以下情况**不应该**拆，拆了反而增加成本：

### 1. 单次选择后的短分支

```renpy
menu:
    "接受":
        y "谢谢"
        jump continue_a
    "拒绝":
        y "……好吧"
        jump continue_b
```

两条分支各 2 句台词，各自汇合回同一处。这应该留在同一模块内，用 if 或 menu 直接处理。为它建两个模块，通信成本远大于收益。

判定：**分支后是否在 30 条事件内汇合**。是则留在同模块。

### 2. 与 NS 标签一一对应

NS 脚本的标签密度和剧情结构不是一回事。一个标签可能只有三行，也可能是整个章节。按标签切片会产生大量无意义的小模块。

### 3. 只有状态差异没有剧情差异

同一段剧情，仅因某个变量不同而显示不同的一句话，这用条件文本处理，不是两个模块。

### 4. 短小的共享段

只有 5 句台词的共享段，复制到两个模块可能比建 call 更简单。判定：**共享段超过约 20 条事件**才值得独立成模块并 call。

## 五、好边界的特征

一个划分正确的模块边界通常满足：

1. **有语义标题**：能用一个短语概括（"雪的文化祭"、"第一次告白"），而不是"第 423 行到第 891 行"
2. **入口状态清晰**：从哪几个地方进入、进去时应该是什么样，能列全
3. **出口意图明确**：跳出去是为了继续什么，不是"跳到这里再看"
4. **内部高内聚**：模块内的事件互相强依赖（同场景、同冲突、同角色）
5. **外部低耦合**：只依赖公共契约中明确定义的角色、变量、素材、函数
6. **可独立验收**：给一个入口状态，能判断模块是否正确

满足其中 5 条即可接受。缺 3 条以上考虑重新划。

## 六、粒度与并行度的关系

模块粒度直接决定能并行多少实现任务：

```
并行任务数 ≈ 可独立实现模块数 / 依赖深度
```

过度拆分会让依赖深度增加（模块 A → B → C → D），实际并行度反而不涨。经验规则：

- 模块数 < 10：串行或 2-3 并行
- 模块数 10-30：按路线分组，每路线内串行，路线间并行
- 模块数 > 30：需要明确依赖层级，同层级并行

## 七、粒度自查清单

在阶段 2 结束时，对每个模块跑一遍：

```text
[ ] 事件条目数 ≤ 300（推荐 80-200）
[ ] 原文行数 ≤ 5000（推荐 800-2500）
[ ] 二级选择点 ≤ 8（推荐 2-5）
[ ] 入口前驱数 ≤ 5（推荐 1-3）
[ ] 出口数 ≤ 6（推荐 1-4）
[ ] 能用一句话概括剧情目的
[ ] 入口状态能完整列出（含每个前驱变体）
[ ] 出口状态能完整列出
[ ] 只依赖公共契约中已定义的对象
[ ] 可以脱离其他模块独立验收
[ ] 拆分后没有裁掉任何台词
```

全部通过才能标 `spec_ready`。任何一项不通过，回阶段 2 重新划分。

## 八、拆分的具体手法

### 手法 1：按场景切分

同一章内有明显场景转换（换背景、换时间、换地点），在转换点切开。这是最自然的边界。

```
common_01_morning    教室，早上
common_01_noon       食堂，中午
common_01_evening    校门，傍晚
```

### 手法 2：按选择点切分

在一个大的选择点之后切开，各分支独立成模块，汇合点独立成模块。

```
chapter_02            前半段，到选择点结束
chapter_02_a          选择 A 后的剧情
chapter_02_b          选择 B 后的剧情
chapter_02_merge      汇合后半段
```

### 手法 3：抽出共享段

多个模块重复的剧情抽成独立模块，各调用方用 call 进入。

```
shared_recap          每周目开头的回顾（被所有路线 call）
```

### 手法 4：溶解过度细分的模块

发现某模块只有 20 条事件且只被一个模块跳转进入，合并进调用方。

## 九、粒度调整的记录

任何粒度调整都要记录：

```text
## STATUS.md 记录
本轮变更：拆分 common_02 为 common_02a / common_02b
原因：原文 6200 行超过上限，且包含 2 个独立场景
受影响模块：common_01（出口指向变更）、common_02_merge（入口变体增加）
```

不要静默重划模块边界——其他会话和实现者依赖这份结构。
