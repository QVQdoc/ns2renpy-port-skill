# 分阶段 AI 任务提示词

主协调者按当前阶段选用下面的提示词，补入实际路径。无需每阶段向用户重新请求许可。
这些是任务模板，不意味着必须开启多个代理；同一 AI 可以分阶段执行。

## A. 全局分析

```text
任务：根据提供的 NS 脚本和素材建立完整游戏蓝图，供之后分模块重建原生 Ren’Py 游戏。

输入：
- 原始脚本：<路径>
- 素材/归档：<路径>
- 已有剧情说明：<路径或无>
- 工作输出目录：<port 目录>

先读取现有 STATUS；有蓝图时继续完善，不重新开始。
从全局理解故事，再把理解保存下来：
1. 写 overview：人物关系、章节、路线、关键选项、汇合及结局。

2. 建 graph：精确节点、边、条件、变量变化、调用返回及交互跳转。
   每条边的条件必须记录三层信息：
   - raw_ns：原始 NS 表达式原样保留（如 "%10 >= 50 && %20 == 1"）
   - normalized：规范化后的可读表达式（如 "yuki_favor >= 50 and yuki_route == 1"）
   - certainty：fully_resolved / needs_verification / unresolved
   不能只写 condition: true/null 而丢掉原始表达式。
   选项的「显示条件」与「选中后执行的条件判断」必须分别记录为
   display_condition 与 condition。

3. 建 catalog：角色、共享变量、素材和公共功能，并保留原始名字映射。
   变量必须标注 scope（save / persistent / local）和 modified_by_modules。
   素材必须标注 status：
   - referenced_not_inspected：只在脚本里见过文件名
   - inspected：已实际检查文件
   - needs_conversion：已检查且确认需要转换
   - ready：已准备好可直接用
   仅列出文件名的素材不得标为 inspected。
   系统功能（存读档、跳过、鉴赏等）也登记在此，
   status 用 native / configured / custom / unsupported。

4. 为剧情整理完整原文及有序事件；事件关联源脚本位置。
   每个事件必须有 wait_for 字段，明确等待原因：
   null / click / timer / music_end / sound_end / animation_end / interaction
   定时等待必须带 duration_ms；动画等待必须带 animation_id。

5. 登记 sources 的四层覆盖状态：
   - read_ranges：已读取
   - parsed_ranges：已成功解析含义（read_ranges 的子集）
   - unparsed_ranges：读过但尚未确定行为
   - unread_ranges：完全未读
   另外必须建立 dynamic_behaviors 数组，登记：
   - dynamic_goto：目标为变量或表达式的跳转，
     记录 raw_code、depends_on_vars、possible_targets
   - implicit_interaction：点击区域、计时推进等隐式交互，记录触发条件和可能目标
   - dynamic_asset_path：变量拼接的素材路径，记录依赖变量
   这三类最容易在静态分析中漏掉，必须是结构化数据，不能只写在正文里。

6. 建 issues：无法确认的内容明确记录，不凭剧情常识补全。

7. 建 mergepoints（汇合点清单）：
   凡是跨模块入边数量 >= 2 的节点，都要在 mergepoints.json 中登记：
   - 节点 ID、所属模块、汇合类型
   - 每个前驱及其离开时的状态（bg / music / 立绘 / 关键变量）
   - 状态冲突时的处理策略
   - verification.status 初始为 unverified
   这一步放在规划阶段做，不要等组装时才发现汇合点状态不一致。

脚本超过上下文时分批读取，合并同一蓝图；已读不等于已解析。
摘要不能取代台词、条件和素材时机。使用变量拼接的路径和动态跳转要追踪赋值。
原脚本与人工剧情表冲突时记录冲突，按用户指定的权威来源处理。
本阶段先完成蓝图，不急于生成全游戏代码。

返回：蓝图路径、覆盖范围（read/parsed/unparsed/unread 各多少行）、
主要路线、汇合点数量、动态行为数量、未解析问题和下一步；
完整细节保存在文件中。
```

## B. 模块规划与公共基础

```text
任务：读取全局蓝图，划分能独立实现、最后能连接的 Ren’Py 模块。

输入：<overview、graph、catalog、issues、mergepoints 路径>
输出：<contracts 和 modules 目录>

按章节、完整事件、路线分支和汇合点划分；小 if 留在模块内部。
共享剧情只有一个归属；每个剧情节点都要有负责模块。
划分后按以下粒度自查（详见 module_sizing_guide.md）：
- 单个模块的 events 条目是否超过 300 条？超过则继续按场景拆分。
- 单个模块的原文是否超过 5000 行？超过则继续拆分。
- 单个模块是否包含超过 8 个二级选择点？超过则考虑拆分。
- 模块入口前驱是否超过 5 个？超过则该节点应独立为汇合模块。
- 模块出口是否超过 6 个？超过则收敛出口。
- 模块是否有明确单一出口语义？同时存在 jump 与 call 返回的需说明理由。
拆分时不得裁掉台词；只允许增加模块数量，不允许减少内容。

为每个模块写自包含任务包：
- 全局简述、本模块目的、负责节点。
- 完整台词与有序事件及来源；太长则按场景继续拆分。
- 需要的角色、变量、素材和公共功能定义（给出实际条目，不是「去 catalog 查」）。
- 各入口的条件及继承画面/音频状态；多前驱时逐个列出。
- 各出口的精确 label、转移方式及状态变化。
- 允许写入路径、只读依赖、验收路径及问题 ID。

统一公共契约版本，固定共享 ID、初始值、接口签名及文件归属。
contracts.md 必须包含版本历史表，每条记录：
版本号、变更内容、受影响模块、兼容性（向后兼容 / 不兼容需重新实现）。
实现公共角色/变量/素材声明和通用 UI；原生系统功能直接复用。
公共功能必须有真实实现或明确的未完成状态，不能以空函数冒充已完成。
系统功能（存读档、跳过、设置、历史、鉴赏）按 system_features.md 的映射方案处理，
需要自写的必须在阶段 3 完成，不要各自在剧情模块里重复实现。
自写功能要提供统一 API（如 port_unlock_cg），不让剧情模块直接操作 persistent。

把本阶段识别到的所有汇合点写入 mergepoints.json；
若规划过程中发现新的多前驱节点，同时补登记。

返回：模块目录与粒度自查结果、依赖顺序、可独立实现的任务、
公共基础状态、汇合点清单。
```

## C. 单模块实现（可重复分配）

```text
任务：根据任务包直接编写一个原生 Ren’Py 剧情模块。

模块：<ID>
任务包：<brief 路径>
事件/原文：<路径>
公共契约：<路径和版本>
允许写入：<本模块路径>

先读任务包及其必要依赖，不重新阅读整个游戏。
使用公共角色、变量、素材和功能，不重复定义，不改其他模块及公共文件。
保持台词原文、条件、选项效果与事件顺序；技术性转义需保证显示结果等效。
按入口条件继承状态，不无条件重置背景、音乐或变量。
本模块若有多个入口变体，实现时必须覆盖每个变体声明的继承状态。
按契约连接出口；call 后应返回，jump 不返回，结局显式结束。

实现每个事件时核对 wait_for：
- dialogue 默认 click 推进；原作有定时推进的必须用计时实现
- wait 类型事件的等待原因不能一律写成 renpy.pause()
- 音效等待与动画等待要分别处理
- 计时事件用 renpy.pause(ms/1000.0)，不要写成固定点击

发现公共接口缺失、原文歧义或依赖不符时，以 issue ID 返回协调者，继续完成无关部分。

实现后核对：
1. 事件覆盖：events.json 中每条 event 是否都有对应实现
2. 选项与条件：display_condition 与 condition 是否分别实现
3. 所有出口：每个出口的 label、转移方式、离开状态是否正确
4. 素材引用：引用的每个素材 ID 是否存在于 catalog 且路径正确
5. 变量修改：修改的变量是否都在任务包允许范围内，
   是否需要更新 catalog 的 modified_by_modules
6. 等待原因：每条事件的 wait_for 是否与实现一致
7. 写法规范：src 来源注释、语义 transform、音频通道、整除写法是否符合
   references/conventions.md；跑一次 `python scripts/nsport_lint.py <game目录>`，
   error 必须为零，warning 逐条决定修复或登记豁免
能使用目标 SDK 时做 lint 检查；没有运行环境则明确标注未做运行验证。

返回并保存 result：
- 实际修改文件。
- 实现节点及入口/出口。
- 读取/修改的共享变量及离开时画面/音频状态。
- 上面 6 项核对的逐条结果、实际运行结果和未验证内容。
- 未解决问题 ID。
```

## D. 组装与验证

```text
任务：将已实现模块组装为完整 Ren’Py 游戏，并按全局蓝图核对。

读取 STATUS、contracts、graph、mergepoints、各模块 result 和实际代码。

一、结构检查
- 节点实现归属：graph 中每个节点是否都有对应实现
- label 连接：所有 jump/call 目标是否存在
- call/return 配对：每个 call 是否有对应 return 路径
- 重复声明：是否有多个模块重复定义了同一角色/变量/素材
- 变量作用域：是否有模块使用了未声明的变量
- 素材路径：所有引用的素材文件是否真实存在
- 公共功能调用：调用签名是否与 contracts 一致

二、汇合点专项检查（按 mergepoints.json 逐条）
对每个汇合点：
- 列出所有前驱路径
- 对每条路径实际运行到汇合点，记录进入时的 bg / music / 立绘 / 变量
- 比对各前驱状态是否与 expected_state 一致
- 检查是否存在前驱未被实际走到（条件不可达）
- 状态冲突时确认 conflict_resolution 是否生效
- 将 verification.status 更新为 state_checked 或 runtime_tested
路径存在不能自动证明条件可达；未实际走通的必须标为 unverified。

三、SDK 验证
使用目标 Ren’Py SDK 执行 lint，并在可用时实际启动。
不用自制静态检查替代 Ren’Py 自身的语法解析与运行。

四、路线与功能验证
- 每个结局是否实际可达
- 条件选项在满足/不满足条件下分别测试
- 共享段从不同入口进入的表现
- 代表性位置的存读档与回滚是否正常（含汇合点位置）
- 系统功能（跳过、历史、设置、鉴赏）是否可用
- 计时等待段落跳过时是否正常

五、如实登记
对尚未跑过的路线、不可达疑点、素材缺口和功能差异如实登记到 issues。
不用静态检查成功替代运行成功。
不为凑完整而擅自补剧情或删除分支。
功能差异标为 accepted_difference 必须由用户明确接受，不能自行认定。

返回：工程入口、逐项检查结果、实际跑过的路线清单、
汇合点验证状态汇总、剩余问题和下一步。
更新 STATUS、validation 和 mergepoints 的验证状态。
```

## E. 新会话续作

```text
继续此移植项目。

先读：
- <port/STATUS.md>
- <port/overview.md>
- 当前契约版本（contracts.md 顶部）
- 若涉及汇合点，读 mergepoints.json

依据下一步记录找到模块任务包；按需读取准确来源，不从头重读全部脚本。

开工前先核对：
- 任务包声明的契约版本与当前契约版本是否一致
- 若不一致，先确认差异及是否需要重新实现
- 模块文件中是否已有人工修改（对比 result.md 记录的文件状态）
- 目标文件是否已被上次会话部分写入

完成当前可执行任务并更新进度，保留未解决问题和实际验证状态；
不把未跑过的标为已验证。
```

## F. 汇合点专项修复

```text
任务：修复指定的汇合点状态不一致问题。

汇合点：<mergepoint id>
当前问题：<描述，如「从 yuki_walk 进入时 bg 是 park，但汇合点期望 school」>

1. 读取 mergepoints.json 中该汇合点的定义
2. 读取所有前驱模块的出口实现，确认各自离开时的实际状态
3. 判断问题类型：
   - 前驱出口状态写错 -> 修前驱模块
   - 汇合点未处理状态差异 -> 修汇合模块
   - expected_state 定义错误 -> 修 mergepoints.json 并记录决定
   - 原作本身就有状态差异（如不同路线保留不同背景）
     -> 记录为 design_decision，不要当 bug 修掉
4. 修复后重新运行所有前驱路径验证
5. 更新 mergepoints 的 verification.status 和 notes

不要为了让状态一致而强行在每个模块开头重置背景音乐，
那会丢失原作的演出连续性。优先在汇合点显式处理差异。
```

## G. 公共契约升级

```text
任务：将公共契约从 <旧版本> 升级到 <新版本>。

变更内容：<描述>

1. 修改 contracts.md，在版本历史表顶部添加新条目
2. 判断兼容性：
   - 新增可选字段/变量/素材 -> 向后兼容，已有模块不用改
   - 修改变量初值、接口签名、返回值结构 -> 不兼容
3. 不兼容时，用 catalog 的 modified_by_modules 找出所有受影响模块，
   逐个列出需要修改的具体位置
4. 更新相关模块任务包中的公共契约版本号
5. 在 STATUS.md 记录本轮变更及受影响模块

不兼容变更后，受影响模块的验证状态回退到 code_review，
不能沿用升级前的 validated 状态。
```
