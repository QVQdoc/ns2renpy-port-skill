# NS → Ren’Py：AI 分模块移植工作流

## 核心思路

先利用 AI 的上下文理解能力，建立对整个游戏的理解，再将理解保存成外部蓝图。根据章节、剧情分支、路线和汇合点划分独立任务；各任务只读取自己的剧情内容和必要的公共定义，分别生成原生 Ren’Py 代码，最后组装。

```text
NS 原始脚本 + 素材 + 已有剧情数据
                ↓
           AI 全局分析
                ↓
 全局蓝图：剧情图、条件、变量、台词、素材、演出、功能
                ↓
     划分模块 + 统一公共契约 + 汇合点登记
                ↓
    公共基础 + 各剧情模块分别实现
                ↓
         组装 Ren’Py 工程
                ↓
  结构检查 → 汇合点核对 → 运行 → 路线核对
```

目标是按原作的剧情结构和可观察行为重新构建游戏。无需逐条复刻 NS 内部机制，也无需另写一套数据运行时。

## 为什么先建蓝图

单独把某段脚本交给 AI，往往缺少路线条件、前后状态及公共约定。先全局理解能确定：故事怎样连接，哪些变量控制路线，哪些剧情共用，素材与功能如何服务演出。

全局理解不能只停留在对话记忆中。它必须保存成文件，让不同会话或不同 AI 都能接着使用。

蓝图保存两层信息：

- 故事摘要：人物关系、章节、路线和剧情目的，用于理解上下文。
- 精确数据：原文、条件、变量赋值、跳转、素材和有序演出，用于实现。

摘要不能替代精确数据。仅知道“这一段两人一起回家”，不足以恢复台词、表情切换、语音和选择结果。

## 这套流程最容易出错的地方

上一版流程的结构是对的，但有几处精度不足，会在实际移植时变成返工。本版针对性地补上了：

### 1. “读过”不等于“理解”

只记录“已读 1-200 行、未读 201-500 行”是不够的。脚本里常见读过但没看懂的段落（动态跳转、变量拼接路径、隐式交互）。这类内容被误当成“已覆盖”，后面就会变成隐藏 bug。

现在覆盖状态分四层：`read` / `parsed` / `unparsed` / `unread`。只有 `parsed` 才算真正理解，`unparsed` 必须挂 issue。

### 2. 动态跳转和隐式交互必须单独登记

`goto *%50` 这种目标取决于运行时变量的跳转，静态分析时根本看不出会去哪儿。点击区域、计时自动推进这类隐式交互同理。它们在脚本里只是几行，但它们决定路线是否连通。

现在 `sources.json` 里有 `dynamic_behaviors` 数组，强制登记三类：`dynamic_goto`、`implicit_interaction`、`dynamic_asset_path`。

### 3. 条件不能只写“有/没有”

原流程的 `"condition": null` 把复杂条件压成了一个布尔值。真正实现时，你需要知道原始表达式是什么、它用到了哪些变量、是否已经确定。

现在条件分三层：`raw_ns`（原始表达式原样保留）、`normalized`（规范化结果）、`certainty`（确定程度）。另外，选项的**显示条件**和**选中后执行的条件**必须分开记录——这两者经常不同，混在一起就实现错了。

### 4. 等待原因必须区分

NS 里有各式各样的等待：等点击、等 N 毫秒、等音效播完、等动画结束。统一写成 `renpy.pause()` 会丢掉演出节奏，甚至卡死。

现在每个事件都带 `wait_for` 字段，取值明确：`null / click / timer / music_end / sound_end / animation_end / interaction`，计时带毫秒数，动画带 ID。

### 5. 汇合点要提前登记，不是组装时才想起来

模块化移植最典型的翻车方式：每条路线单独实现都对，拼起来背景错、音乐叠、立绘残留。原因是汇合点从来没被当成一个需要核对的对象。

现在新增 `mergepoints.json`，在**模块规划阶段**就把所有跨模块的多入边节点登记下来，写明每个前驱离开时的状态、冲突处理策略、验证状态。组装时按清单逐条核对，而不是靠印象。

配套的 [汇合点验证指南](../references/mergepoints_guide.md) 给了静态核对和运行核对的具体做法，包括往汇合点插调试代码批量收状态的手法。

### 6. 模块粒度要有硬指标

“以章节、完整事件作为边界”太主观。不同人划出来的模块大小可能差十倍，直接影响能不能在一个上下文里实现完。

现在 [模块粒度指南](../references/module_sizing_guide.md) 给了硬上限（事件 ≤300、原文 ≤5000 行、二级选择 ≤8、入口前驱 ≤5、出口 ≤6）和推荐区间，也给了“哪些情况不该拆”的信号——过度拆分会让依赖深度吃掉并行收益。

### 7. 系统功能要有统一策略

存读档、跳过、历史、设置、CG 鉴赏这些，原流程只说“优先用原生”。但原生覆盖不了的部分（地图选择、鉴赏模式）如果让每个剧情模块各自实现，后面加一个功能要改几十处。

现在新增 [系统功能映射](../references/system_features.md)，给了每个功能的实现策略、统一 API 要求（如 `port_unlock_cg()`），以及原生配置的具体写法和常见陷阱（用 `define` 定义需要存档的变量之类）。

### 8. 进度状态要能看出卡在哪

把 `implemented` 一个状态同时表示“代码写完”“lint 过了”“跑通了”，等于没区分。现在模块状态细分为：

```text
planned / spec_ready / implementing / code_review /
lint_pass / runtime_tested / validated / blocked:<issue_id>
```

STATUS.md 也增加了汇合点验证表，能一眼看到哪些汇合点还只是静态核对过。

### 9. 缺一张统一的 NS → Ren'Py 写法对照表

原流程只说了“用原生能力实现”，没规定同一段演出应该写成什么样。结果就是自由发挥：立绘有的用 `at left`、有的写裸坐标，过渡有的用 `Dissolve`、有的照抄旧转换器的 `with dissolve`，跳过、鉴赏这类功能每个模块各造一份。

现在新增 [功能对照表](../references/ns_to_renpy_map.md)，逐条给出 NS 功能 → Ren'Py 官方写法，每条都标官方出处（NScripter Reference 命令页、Ren'Py 官方文档），并按三档判定：

- **A 官方对应**：用原生写法，不写自定义代码
- **B 官方近似**：用原生 + 调参，差异必须写进 result.md
- **C 无对应**：走统一 API，全局只有一份实现

查官方文档时纠正了几处凭经验容易写错的地方：

| 项 | 常见误解 | 官方实际 |
|---|---|---|
| `print` | 输出文字 | **按效果重绘屏幕**；`0`=只写内存不显示，`1`=瞬时，`>1`=调 `effect` 自定义 |
| `wait` vs `delay` | 都是等一会儿 | `wait` 点击**不能**跳过，`delay` 点击**可以**跳过 |
| `lsp` 坐标 | 图中心 | 官方写明是**左上角像素**，Ren'Py 必须显式 `xanchor=0` |
| `rnd %v,N` | 0~N | 0~**N-1**，上界取不到 |
| `div` | 可用 `//` | 官方是"舍去小数"，`//` 对负数向下取整会差 1 |
| effect 编号 | 有通用映射表 | `0`/`1` 是固定值，**2 以上由作品自己用 `effect` 定义**，无通用表 |

配套新增 [写法规范](../references/conventions.md)，核心是一条：**每条转换来的语句带 `# src:<源文件>:<行号>` 注释**。这样半年后改一句台词，能直接打开 NS 原脚本对应行确认；改坏了也能判断是移植错误还是原作文本如此。规范还定了文件组织、命名、位置/过渡/音频写法、禁止清单。

规范能机器检查：[scripts/nsport_lint.py](../scripts/nsport_lint.py) 会扫出裸坐标、`//`、缺来源注释、story 里定义公共对象、裸 TODO 等问题，输出 error/warning/info 和来源注释覆盖率。error 清零才能进组装。

它和旧的 `mapping.md` 是两回事：mapping 是转换器的输出契约（产物形如 `show ns_bg_a zorder -100`），对照表是**实现者的查阅手册**，目标是原生写法。

### 10. 素材和演出层不能每个工程各手搓一份

前九条都是「理解和写法」的问题，这一条是**执行载体**的问题，也是在真实游戏上第一次跑通全流程时暴露的：素材转换脚本里写死了 `bg/ chr/ ev/` 三个目录，换个游戏就要重写；立绘的双宽蒙版图（左半图像 + 右半遮罩）被当普通图直接转 PNG，人物背后一块绿。更隐蔽的是把 NS 的分层照抄成 `scene`/`show`：`scene` 换背景会连立绘一起清掉。

现在这三处各有通用件：[nsassets.py](../scripts/nsassets.py)（普查）、[convert_assets.py](../scripts/convert_assets.py)（转换）、[ns_stage.rpy](../assets/ns_stage.rpy)（演出层）。细节见下一节「素材与功能怎样实现」和 [素材与演出层契约](../references/assets_contract.md)。

### 11. “文件更新”不等于“文件能用”

过场动画踩过一次：`opening.webm` 是上一轮手工 ffmpeg 转的 VP9，比源文件新，于是转换脚本的幂等判据放它过去了。结果 Ren'Py 8.5 播 VP9 时 `movie_cutscene()` **永久阻塞**——黑屏、不报错、日志干净、CPU 接近 0，看起来像死循环，实际是解码器不返回。

所以幂等判据不能只看时间戳：`ns_movies.py` 现在跳过前用 ffprobe 复核编码（固定 VP8），并提供 `--verify` 只查不转；走线探针会把 `movie_cutscene` 打桩，动画必须单独复核。同类的「看起来没问题」还有：音频登记了但路径大小写不对、素材有 alpha 但键色没抠干净——都只能靠实测与肉眼，不能靠「跑起来没崩」。

### 12. 一张静态帧不等于一段动画

开场 LOGO 又踩了一次：早期脚本把 `sys/01.bmp`（LOGO 落定帧）直接复制成 `logo.png`，移植版就只放这张静态图。可原作是「从屏幕右侧 4 段滑入（`msp 0,-200,0,0` ×4 + `waittimer 60`）→ 换成 10 格翻转动画（`lsph 1,":c/10,40,1;sys\tlanime.bmp"`，40ms/格）→ 停 2 秒 → 随机一句 TOUCHABLE 语音」。少了帧序列，剩下的就是一个静止的画面。

现在的做法：spec 第 2 参数（每格毫秒）> 0 的多格素材，由 [convert_assets.py](../scripts/convert_assets.py) 生成 `<名>_anim`（播一遍）/`<名>_loop`（循环）两个 image 并登记进 `NS_STRIPS`，剧情里用演出层的 `ns_strip()` 播；`msp` 那种逐帧滑动按原作段数硬等复刻。判断一个素材「是不是在演」看源脚本：同一个精灵被反复 `msp`/`vsp`/`csp`/`waittimer` 摆弄，就一定是动画，别用静图糊过去。

顺带一个坑：素材名在生成时被归一化（`sys\01.bmp` → `sys n01`），手写流程代码照原作写 `ns_strip("sys", "01")` 原本会命中不了、显示成灰块，而 lint 报 0 error。现在两头都补了：`ns_stage.rpy` 里的 `ns_safe()` 在运行期兜底（先按原样试、再按归一化名试），`nsport_lint` 的 `NS016` 拿生成件做静态对账。遇到「转好了却没显示」，先看 `NS016` 与运行期 `NS_MISSING`，别只看 lint 的 error 数。

### 13. 别把 `_bg` 当成“只换背景”

同一个语义陷阱的第三次翻车。NS 里背景、CG、黑幕、纯色**全走 `_bg`**，而 `_bg` 会连 `ld` 上的立绘一起清掉。原作一直按这个前提写：

```
0.txt:1572  black                    ← 立绘 s02_e 还在
0.txt:1574  bgchr "street_c","s02_i"  ← 要带人就用 bgchr
0.txt:10677 black                    ← 立绘 s03_a 还在
0.txt:10684 bg "room"                ← 换到自己房间，人已经不在场，没有 chr ""
0.txt:2509  ev "32a"                 ← CG 单独占满画面，人物消失
```

作者的词汇表很干净：`bg` = 换景（人物随之消失）、`bgchr` = 换景并带人、`chr` = 只换人、`chr ""` = 同景内退场。第一版演出层按“Ren'Py 里 show 背景不会清立绘”的直觉写成全部不清，结果就是「人物在场景切换时没有按脚本消失」。

现在的规则：`ns_bg`/`ns_ev`/`ns_black`/`ns_color` 默认清立绘（`clear_chr=True`），「换景并带人」只有 `ns_bgchr` 一个入口；`lsp` 的怪物/UI 精灵**不**跟着清，因为原作对这些一律显式 `csp`（`0.txt:2259` lsp / `2280` csp）。判断依据不是猜，是数出来的：剧情区 389 处 `bg`/`ev`/`black` 里有 198 处切换时立绘在场，其中 130 处之后没有任何 `chr` 调用、59 处紧接着重新 `chr`——两种都只在“`_bg` 会清立绘”的前提下才成立。

这一节写的是“为什么”，**逐条的症状 → 根因 → 解法表在 [SKILL.md 的实测踩坑清单](../references/pitfalls.md)** 里（七类共 51 条，含验证层、环境层、界面层与打包发布层的坑）。补坑时两边都要动：这里补一段“为什么会上当”，SKILL 里补一行“下次怎么绕开”。

## 怎么避开上下文限制

分析阶段能整体读取就整体读取；原始游戏超过窗口时，按文件或章节分批分析，合并同一蓝图，并记录已读、已解析与未解析区间。

实现阶段不再重复读取全游戏。每个任务只需要：

1. 全局故事简述。
2. 本模块依赖的公共角色、变量、素材和接口定义（直接给出条目，不是让人去翻目录）。
3. 本模块完整台词、条件和有序演出。
4. 入口、出口及需要继承的状态。

长模块继续按场景拆分，原文保持完整。减少上下文靠拆分和索引，不靠删减细节。

## 模块怎样划分

优先用章节、完整事件、较长支线、路线入口及汇合点作为边界。小范围 if 留在模块内，不必每个条件都单独成模块，也不必与 NS 标签一一对应。

例如：序章、共同线第一章、雪的事件、玲的事件、共同线第二章、雪路线、玲路线。

共用剧情只有一个实现归属，由不同模块调用或跳转进入。入口可能来自多个分支，各分支带来的画面、音乐和变量状态必须分别说明。

划完要跑一遍粒度自查，超出上限就继续拆——只增加模块数，不裁台词。

## 素材与功能怎样实现

素材尽量复用，先核对真实文件、路径和格式；需要时解包并转换遮罩、透明方式或精灵帧。素材目录包含原路径到新路径的对应。

素材状态必须是四选一：`referenced_not_inspected` / `inspected` / `needs_conversion` / `ready`。只在脚本里见过文件名，不能标成已检查。

节点内按执行顺序记录背景、立绘、表情、音乐、语音、等待、台词和选项，每条带等待原因。仅列出“用过哪些素材”不能表达演出时机。

### 素材转换与演出层：通用件，不是每个工程手搓

实测最容易翻车的两处就在这里：

- **素材调用不通用**：上个工程写了个「遍历 `bg/ chr/ ev/` 三个目录、BMP 转 PNG」的临时脚本，换个游戏就得重写一遍。目录名、spec 前缀（`:a;` / `:#RRGGBB` / `/N,dx,dy;`）、变量拼接的路径全都不在里面，等于每次都靠临场猜。
- **立绘蒙版没处理**：NS 的立绘常把「图像 + 遮罩」拼成一张双宽图（本例 1166×600），左半是图、右半是遮罩。直接转 PNG 会得到「绿幕方块 + 多出半个遮罩」的立绘，人物背后一块绿。

现在这层由三件通用件负责，工程里只放数据、不放实现：

| 文件 | 作用 |
|---|---|
| [nsassets.py](../scripts/nsassets.py) | 从脚本抽全部素材引用（含变量路径、spec、`defsub` 包装层）→ 到磁盘核对尺寸与像素 → `assets_manifest.json` + 普查报告 |
| [convert_assets.py](../scripts/convert_assets.py) | 按 manifest 转图：拆蒙版、抠键色、切分割、RGB 渗色、文件名合法化，并生成 `port_images.rpy` / `port_wrappers.rpy` |
| [ns_stage.rpy](../assets/ns_stage.rpy) | 演出层运行时：背景/CG/黑幕共一层、立绘独立，`ld`/`cl`/`lsp`/`dwave`/`bgm` 全走它 |

配套的 [素材与演出层契约](../references/assets_contract.md) 写清了 spec 语法、manifest 结构、生成文件契约和调用边界。其中两条是最容易弄反的：

- **带分割的蒙版先切格、再拆蒙版**：`:a/2,0,3;` 是「每格一对 `[图|罩]`」（标题按钮就是这样）。顺序反了 alpha 会错位半格 —— 按钮看着发虚、绿底反而留下。
- **脚本写了 spec 就按 spec**：像素探测只补没有 spec 的素材。`sys/tlanime.bmp` 那种 10 帧动画条，横切两半「看着像」图+遮罩，按像素判会把每一帧都拆碎。

**为什么演出层不能省**：NS 的分层规则和 Ren'Py 的直觉不一样——`_bg` 换背景层的同时会把 `ld` 的立绘清掉，`lsp` 的分散精灵却要显式 `csp` 才收；Ren'Py 的 `scene` 又是整层清空。三种语义混着写，必然出现「该消失的没消失、该留下的被清掉」。演出层把这件事固定下来，并且 lint 用 `NS012`/`NS013`/`NS014`（外加 `NS015` 盯「又贴了一张手搓 `images/xxx.png`」）守住边界。

素材这一层的验收用数字看：普查 `missing=0`、蒙版张数与实际相符、转换后立绘无绿幕/无遮罩半幅、换背景不掉立绘。

音频这一层的坑是**运行期不允许注册通道**：NS 的 `dwave 1+%SENUM` 是「通道号 + 起停」，Ren'Py 侧要给每个通道建 `ns<n>`，而 `register_channel()` 只在 init 有效，写在播放函数里就会在第一次播 SE 时抛 `Can't register channel outside of init phase`。演出层因此在 `init -5` 把 `ns1..ns32` 一次建好，运行期只查表、越界退回 `sound`。

落实到 Ren'Py 时，逐条查 [功能对照表](../references/ns_to_renpy_map.md)，按三类分别处理：

| 类别 | 含义 | 做法 |
|---|---|---|
| A 直接对应 | 原生有等价语义 | 用原生，不写自定义代码 |
| B 语义近似 | 原生能表达但默认行为不同 | 用原生 + 调整，差异写进 result.md |
| C 需自定义 | 原生没有对应能力 | 走统一 API，且只有一份实现 |

大类对应关系概览：

| 原作行为 | Ren'Py 实现 |
|---|---|
| 剧情节点与转移 | label、jump、call/return |
| 选项与路线判定 | menu、if、共享变量 |
| 背景和立绘 | scene、show、hide、Transform |
| 移动及过渡 | ATL、Transform、transition |
| 音乐、音效、语音 | play、stop、voice |
| 地图、图片按钮、特殊交互 | screen、imagebutton、imagemap |
| 存读档、历史、设置 | 优先使用原生系统 |
| CG 鉴赏、音乐鉴赏 | 自写 screen + 统一解锁 API |

具体到单条语句的写法、坐标锚点、`div` 截断、`rnd` 区间、一页多行改多条 say、效果编号不可通用等细节，全部在对照表里，不在本文重复。

## 怎样让各模块最后拼起来

先统一公共契约：角色 ID、变量名称与初始值、素材 ID、label、screen/函数接口和文件归属。每个任务带契约版本。

契约必须带**版本历史表**，记录每条变更的受影响模块和兼容性。不兼容变更后，受影响模块的验证状态要回退，不能沿用升级前的 `validated`。

公共角色、变量、素材声明及通用 UI 先实现一次。剧情模块只写分配的文件，不各自重新定义公共内容。发现公共接口缺口时交回主协调者处理。

模块返回时说明入口/出口、修改的状态、实现节点、问题及实际验证结果。组装时重点核对跨模块连接和分支汇合后的状态。

## 工作流中的验证

验证服务于重建，不要求套用旧转换器的修复流程。

验证顺序：

1. **结构检查**：节点归属、label 连接、call/return 配对、重复声明、变量作用域、素材路径、接口签名。
2. **汇合点核对**：按 `mergepoints.json` 逐条走前驱，比对进场状态。未实际走通的前驱标 `unverified`。
3. **SDK 验证**：用目标 Ren’Py SDK 做 lint 并实际启动。自制静态检查不能替代。
4. **路线与功能验证**：各结局、条件选项、共享段、存读档与回滚、系统功能。

图上存在路径不代表条件一定可达。未实际运行过的内容如实标记未验证。缺失功能和未确定行为登记问题，不能静默删掉后宣称完成。

汇合点的整体状态取所有汇合点的最低值——不能因为大部分没问题就标整体通过。

### 全量走线：先把整条剧情跑通，再谈精修

模块级验证只能证明「这一段能跑」。整部作品的坑通常藏在**规模**上：素材名大小写、多目录音频探测、只在某章出现的命令变体、
某条分支永远进不去的死标签。这些在搬一个模块时全都看不到。

所以移植到一定进度后，用一对通用件做一次「整部机械移植 + 全量走线」：

- `scripts/ns2renpy_story.py` 按 `graph.json` 的标签区间把全部剧情机械翻成 `story/gen_*.rpy`（底稿），出逐标签覆盖报告；
- `scripts/nswalk.py` + `assets/ns_autowalk.rpy` 按菜单分支把整条剧情真跑一遍，收 `missing_assets` / `bad_runs` / 未进入的标签。

判定标准只有一条：**台词行覆盖要等于生成器统计的总数，未进入的标签要能逐个解释**（结局另一侧、纯跳转别名标签）。
「游戏能启动」「lint 过了」都不算跑通。

## 如何开始

将 ns-port 文件夹交给支持该 Skill 格式的工具加载，或直接让 AI 阅读其中的 SKILL.md。仅复制文件并不会自动安装或启用 Skill。

可使用下面的启动提示词：

```text
请读取 ns-port/SKILL.md，按其中的全局蓝图驱动工作流，
将我提供的 NS 游戏重建为原生 Ren’Py 游戏。

脚本位置：<实际路径>
素材位置：<实际路径>
已有剧情数据：<实际路径或无>
输出工程：<实际路径>
目标 Ren’Py SDK：<版本或待确定>

先建立全局蓝图（含读取覆盖、动态行为、条件表达式和汇合点），
再按剧情结构划分自包含模块并跑粒度自查，
统一公共定义后分别实现，组装时按汇合点清单逐条核对。
进度保存在 port/STATUS.md；后续会话从记录继续。
```

本包提供的是工作方法和模板。尚未对具体游戏执行移植，也未验证任何真实作品的 Ren’Py 运行结果。
